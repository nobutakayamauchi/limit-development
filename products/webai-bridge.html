WHY

AIはできた。
で、どうやって渡します？

AIそのものを作るところまでは速くなりました。面倒なのはその後です。誰に使わせるか、どう課金するか、推論代を誰が払うか、Knowledgeをどう持たせるか、買った人だけにどう開けるか。そこを毎回ゼロから作ると、配布するたびに別のサービス開発が始まります。

「便利なAIを作った」から、
「人に渡して使ってもらえる」までが遠い。

AIを作る → 販売ページを作る → 決済を作る → 利用権を作る → APIキーを扱う → Knowledgeを持たせる → 配布する → 失効も考える。

WebAI Bridgeは、この「その後」をまとめるために作っています。

ONE PACKAGE

AIの中身と、
売り方を分けて持つ。

WebAI Bridgeでは「AIそのもの」「アクセス条件」「推論代の支払者」「届け方」を別々に扱います。だから売り方や利用方法が変わっても、AIの中身まで全部作り直す必要がありません。

01 / AI PACKAGE

AIの中身

名前、説明、Instructions、Knowledge、利用するモデルやルーティング方針をひとまとめにします。

02 / ACCESS

誰が使えるか

無料、買い切り、サブスク、従量など、AIそのものとは別に利用権を扱える設計です。

03 / INFERENCE PAYER

推論代を誰が払うか

BYOK、利用者クレジット、提供者負担などを別レイヤーとして扱います。初期提供はBYOKを中心にしています。

04 / DELIVERY

どう届けるか

Hosted URL、持ち運べるPackage、または両方。用途に合わせて配布方法を切り替える前提です。

大事なルールは、かなり単純です。
ACCESS PRICE != INFERENCE COST

購入代金と、AIを動かす推論代は別。
誰が推論代を払うか決まらない限り、モデルは動かさない。
HOW IT WORKS

作る。売る。渡す。
そのまま使ってもらう。

01 / CREATEAIをまとめる

Instructions、Knowledge、説明、モデル設定をPackageとしてまとめます。

02 / PUBLISH公開する

Creator StudioからHosted商品として公開。購入者向けURLを作ります。

03 / SELL購入してもらう

Stripe決済と利用権をつなぎ、買った人だけが先へ進めるようにします。

04 / RUNその場で使う

購入者が自分のAPIキーを接続し、あなたのKnowledgeを使ったAIを動かします。

REAL COMMERCIAL CHAIN PROVEN

スマホから作って、実決済して、購入者として使うところまで。

固定ドメインHTTPS、Creator Studio、2商品目の公開、Stripe実決済、購入者への受け渡し、BYOK、Knowledge参照、AI応答、利用権失効、その後の即時拒否までを実機で通しています。

実装も、失敗も、GitHubにあります。

WebAI Bridgeは販売用の説明だけを先に作っているものではありません。Runtime、Creator Studio、Package schema、課金境界、デプロイ検証を実装側で分け、実機テストで出た問題を戻しながら詰めています。
