# Product Card → LP Playbook

Purpose: ship and sell new work without rebuilding the marketing structure every time.

## Trigger

When a new GitHub repository appears, do not immediately invent a product page.
Run a short wall-ball interview first.

Ask:

1. What is the formal name / nickname?
2. What should the user **do / stop doing**? Aim for one memorable sentence.
3. In plain language, what does this do?
4. Who is it for, and what annoying situation does it solve?
5. What goes in?
6. What comes out?
7. What does the human still decide / do at the end?
8. What single visual would explain it fastest?
9. Is it a production, research item, or paid product/service?
10. What is the next action: use it yourself, read details, ask for setup, or buy?

Do not skip the wall-ball step. The short copy is the source for everything below.

---

## Carousel card: 3-second version

```text
[NAME]

[Do this. / Stop doing this. / Problem? Start here.]

[2 short lines explaining exactly what it does]

[One short definition: "___ tool / method / service."]
```

Examples already adopted:

- FOUNDRY GROWTH ENGINE — **仕事してください。**
- Ultimate Loop — **一からの新造、やめてください。**
- BridgePatch — **ここ直せば、大体直ります。**
- AXIS — **たくさんあっても、今やるのはこれだけです。**
- NAGI — **中断した場所？ここからです。**
- TRACE — **「何が起きた？」慌てずこれ見てください。**

The carousel must explain the product to a non-engineer before they click.
Technical theory does not belong here.

---

## Visual: 10-second version

Make one visual that shows:

```text
problem / input → what the tool does → result / output → human final action
```

Prefer one scene or one flow. Avoid architecture diagrams unless the architecture itself is the product.

---

## LP: 3-minute version

Use this sequence. It is intentionally simple: PAS-style problem recognition + proof + direct CTA.

1. **Killer copy** — reuse the carousel headline.
2. **What is it?** — 2–4 plain-language lines.
3. **Ever had this?** — one familiar before-state, no fear marketing.
4. **What it does** — 3–4 steps max.
5. **One visual** — the fastest explanation on the page.
6. **What changes** — simple Before / After.
7. **Proof** — real repository, screenshots, logs, examples, or measured results only. No invented metrics.
8. **Good fit / bad fit** — let people self-select.
9. **How to use it** — 3 steps max.
10. **Details** — separate technical spec / GitHub link.
11. **Offer** — DIY / setup / integration / maintenance as applicable.
12. **CTA** — one primary action, one secondary action at most.

Rules:

- Explain meaning before mechanism.
- One section = one job.
- Short Japanese beats jargon.
- Do not auto-publish or imply unsafe automation when human approval is part of the product.
- Proof must be inspectable.
- If pricing is not fixed yet, sell the consultation/setup first rather than blocking launch.

---

## Sales-first release order

```text
NEW REPO
→ INTERVIEW
→ CARD COPY
→ VISUAL
→ LP
→ CTA
→ PUBLISH
→ SEND TRAFFIC
→ OBSERVE QUESTIONS / SALES
→ EDIT COPY
```

Do not build a full marketing system before the first sale.
The first goal is to learn what real visitors ask, misunderstand, and pay for.
